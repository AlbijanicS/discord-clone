# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A learning-focused Discord clone built with Elixir, Phoenix LiveView, Ecto/PostgreSQL, and OTP (GenServer / Registry / DynamicSupervisor). See `project.md` for learning goals and `CONTEXT.md` for the domain glossary (the canonical vocabulary — e.g. "Workspace" not "Server", "Workspace Member" not "Participant"). Per-feature PRDs and issue logs live in `docs/`.

**`AGENTS.md` holds the detailed Phoenix v1.8 / LiveView / Ecto / Elixir framework conventions and is authoritative for all framework-level decisions — read it before writing web-layer or schema code.** This file only covers project-specific architecture and commands.

## Commands

- `mix setup` — install deps, create/migrate DB, build assets (first-time setup)
- `mix phx.server` (or `iex -S mix phx.server`) — run the app on localhost:4000
- `mix test` — auto-creates and migrates the test DB, then runs the suite
- `mix test test/path/to/file_test.exs` — run one file; append `:LINE` for one test; `mix test --failed` reruns last failures
- `mix precommit` — **run when done with changes**: `compile --warnings-as-errors`, `deps.unlock --unused`, `format`, `test`. Fix everything it reports.
- `mix ecto.gen.migration name_in_snake_case` — always generate migrations this way (never hand-write the timestamp)
- `mix ecto.reset` — drop, recreate, migrate, seed

## Architecture

Three-layer split: **contexts** (`lib/discord_clone/`) own all business logic and data access; the **web layer** (`lib/discord_clone_web/`) is thin LiveViews/controllers; an **OTP runtime** under the Chat context holds ephemeral real-time state.

### Contexts (`lib/discord_clone/`)

- **Accounts** — users, tokens, notifiers. Generated by `phx.gen.auth`.
- **Workspaces** — workspaces, memberships, channels, invites, bans, and moderation (mute/timeout). Permission helpers (`owner`/`admin`/`member` roles) live here and gate all mutations. Schemas in `workspaces/`.
- **Chat** — persisted messages, reactions, read state / unread spans, plus PubSub orchestration and the live process runtime. Schemas and runtime modules in `chat/`.

**Auth boundary:** `phx.gen.auth` uses a `Scope` (`DiscordClone.Accounts.Scope`), NOT a bare `current_user`. Context functions take `%Scope{}` as the first arg and filter queries by `scope.user`. In templates/LiveViews use `@current_scope.user` — never `@current_user`. See the Authentication section of `AGENTS.md`.

### OTP runtime (`lib/discord_clone/chat/`)

Supervision tree children are started in `application.ex`: two `Registry` + `DynamicSupervisor` pairs plus `Phoenix.PubSub`.

- **WorkspaceServer** (one GenServer per active workspace, keyed in `WorkspaceRegistry`, started under `WorkspaceSupervisor`) — tracks online presence for a workspace. Started on demand via `WorkspacePresenceRuntime`. Presence changes broadcast over PubSub (`WorkspacePresence`), consumed by LiveViews.
- **ConversationServer** (one GenServer per active Conversation, keyed in `ConversationRegistry`, started under `ConversationSupervisor`) — in-memory cache of recent Messages and transient typing indicators for either Conversation kind. Idle Conversations shut down after a 15-minute inactivity timeout; the supervisor reloads recent Messages from Postgres on next start. Authorization remains in public contexts rather than this kind-agnostic runtime.

Rule of thumb: **durable state → Postgres via Ecto; ephemeral real-time state (presence, typing, hot message cache) → these GenServers.** LiveViews read/write through the Chat context, which delegates to the runtime and broadcasts via PubSub.

### Web layer (`lib/discord_clone_web/`)

- LiveViews grouped by area: `workspace_live/` (home, entry, shell, presence, audit log, invites, member actions menu), `channel_live/` (message view + rows), `user_live/` (auth screens).
- Controllers only for non-LiveView flows: `invite_controller` (accept invite via link), `user_session_controller`.
- Routes in `router.ex` are split across `live_session :require_authenticated_user` (workspaces, channels, settings) and `live_session :current_user` (register/login). Follow the router placement rules in `AGENTS.md` when adding routes.
